Implementation Plan for Marketplace and Withdrawals
Proposed Changes
1. Dashboard: Filter Start Work Modal to Claimed Projects
We need to restrict the "Start Work" modal so that users can only select projects they have explicitly claimed.

[MODIFY] 
src/pages/Dashboard.tsx
Refactor 
loadJobs
 to fetch only from project_assignments (joining client_projects) and job_contract_claims (joining job_contracts) where the designer_id matches the current user.id.
This ensures the Start Work modal no longer displays the entire public pool of pending projects, completely restricting it to the user's claimed contracts.
2. Active Contracts: Add Unclaim Button
Users need the ability to back out of a claimed project directly from their active projects list.

[MODIFY] 
src/components/dashboard/ActiveContracts.tsx
Ensure the source type (e.g., client_projects, job_contracts, client_orders) is passed correctly into the 
ActiveContract
 state.
Add an "Unclaim" button to each card.
Create a handleUnclaim function that deletes the corresponding row from project_assignments or job_contract_claims, or resets assigned_designer_id for legacy client_orders.
Refresh the active contract list on success.
3. Submit Work: Restrict to Claimed Projects
Only projects that have been claimed and started should be visible for submission.

[MODIFY] 
src/pages/SubmitWork.tsx
Update 
loadJobs
 to fetch existing claimed projects via project_assignments and job_contract_claims rather than fetching all active job contracts.
This fully restricts the dropdown of available jobs to only what the user has claimed, satisfying Goal 3.
4. Marketplace: Actual Deadline and Reward Value
The marketplace should be totally transparent about project deadlines and true rewards based on the DB schema.

[MODIFY] 
src/components/dashboard/ProjectMarketplace.tsx
Update the Dialog content (Project Brief) to display the actual deadline from the selected order, avoiding the hardcoded Standard Deadline: 2 Days.
If no deadline is set, explicitly denote it (e.g. No strict deadline defined).
Ensure the budget or price is cleanly rendered in the Project Brief.
[MODIFY] 
src/pages/Marketplace.tsx
No major structural changes required here since 
ProjectMarketplace
 handles the heavy lifting, but will verify aesthetics match.
5. Withdrawals: SuperAdmin Finance Hub Approval
Withdrawal requests from the dashboard must go into a pending bin to be approved by the SuperAdmin, who actually triggers the Korapay payout to the user's saved payment method.

[NEW] supabase/migrations/2026xxxx_add_withdrawal_insert_policy.sql
Generate an SQL migration to add an RLS policy allowing authenticated users to INSERT into public.withdrawals as long as auth.uid() = user_id. This allows us to securely log their request as pending directly from the dashboard.
[MODIFY] 
src/components/dashboard/WithdrawCard.tsx
Change 
submitWithdrawal
 to perform a straightforward supabase.from('withdrawals').insert({ ... status: 'pending' }) rather than invoking the request-withdrawal edge function (which we assume attempts instant payout).
[MODIFY] 
src/pages/FinanceDashboard.tsx
Add a new "Pending Withdrawal Requests" table below or near the Ledger section.
Fetch pending withdrawals joining with payout_methods and profiles.
Add an "Approve via Korapay" button for each request. When clicked, this will invoke the request-withdrawal or similar Korapay-integrated edge function dynamically with the specific withdrawal DB record.
